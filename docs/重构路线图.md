# 重构路线图（v0.4.0 起 · 性能与质量重构）

> **地位**：当前活跃开发计划，位于 `开发总纲.md` 之下、各阶段文档之上。总纲锁定范围与选型不变；本路线图只做工程级重构。
> **依据**：`瓶颈分析报告.md`（2026-09-06 全链路代码审计）。
> **制定日期**：2026-09-06

---

## 1. 重构目标（可量化）

| 维度 | 现状 | 目标 |
|------|------|------|
| 首次可见时间 | 全文翻译完才有任何内容（2–4 分钟） | 文本层 PDF 上传后 **≤ 3 秒**可见全文原文 |
| 译文呈现 | 一次性 | **逐段渐进流入**，边译边读 |
| 术语一致性 | 同一术语跨批次漂移 | 抽检 5 个术语全文译法一致 |
| 双栏对齐 | 字符数估算，错位漂移 | 左右**结构化同行对齐**，零漂移 |
| 稳定性 | _jobs 内存泄漏、截断静默降级 | 连续 10 份 PDF 内存平稳、截断自动重试 |

## 2. 总原则

1. **渐进式重构，不推倒重来**（决策 ADR-R0）：现有栈（Tauri/React/FastAPI/文本层优先/合并批量）经审计 80% 正确，推倒重写是负收益。
2. **每阶段独立可交付**：阶段结束 = 可用版本 + tag + 回填文档，任何时刻停下项目都处于可用状态。
3. **感知优先**：先解决"用户看得到的"（渐进呈现），再解决"用户感受到的"（质量），最后解决"天花板"（渲染路线）。
4. **遵守总纲约束**：不改锁定选型；阶段 4 若要走原生渲染，属新决策 **D6**，必须由用户确认后方可动工。

5. **完成记录回填**到阶段文档（日期、文件清单、遗留问题）。
6. 合并 `dev → master`，打 tag（按 `版本规划.md` 语义化版本）。
