# 瓶颈分析报告（全链路代码审计）

> **日期**：2026-09-06 ｜ **性质**：重构路线图（v0.4.0 起）的立项依据
> **方法**：逐文件阅读 processor.py / openai_compat.py / textlayer.py / siliconflow.py / useOcr.ts / BilingualPage.tsx / InlinePage.tsx / MarkdownText.tsx / main.py / bridge.ts 后得出，非猜测。
> **触发背景**：用户反馈翻译速度慢、翻译效果差、排版乱，要求判定"技术选型问题还是细节优化问题"。

---

## 1. 总判断

**技术选型 80% 正确（不推倒重来），但三个架构级决策分别钉死了速度、质量、排版的上限；剩余 20% 是细节缺陷。** 之前的修复（模型升级、并发调整、数据清理）都属细节层，因此"一直在修但体感没有质变"。

| 问题 | 性质 | 根因一句话 |
|------|------|------------|
| 翻译速度慢 | **架构级** | 全量批处理 + 前端只在全部完成后渲染，感知速度为零 |
| 翻译效果差 | **架构级** | 逐段盲译，无文档级术语表与上下文 |
| 排版乱 | **架构级（选型天花板）** | 丢版面坐标的 Markdown 重建路线 |
| 其余 | 细节 | 连接池、缓存版本、回退串行、内存泄漏等 |

## 2. 速度瓶颈

### 2.1 根因：渐进呈现能力被前端废掉
- `backend/pipeline/processor.py:197` 后端特意提前挂载 `job["pages"]`（注释写明"前端轮询即可渐进看到已完成的译文"），翻译过程中逐段原地更新。
- **但 `src/hooks/useOcr.ts:50-53` 只在 `status === "done"` 时才 `setPages`，中间轮询数据全部丢弃**；且 `isLoading` 全屏遮罩（BilingualPage:19 / InlinePage:18）让用户连毫秒级可得的原文都看不到。
- 后端建好的能力被前端一行代码废掉。这是**最大单点**。

### 2.2 量化
12 页论文 ≈ 400+ 段 → 47 个批次请求（10 段/批）→ 8 并发 6 波 × 每批 15–40s ≈ **2–4 分钟全程空白**。知云/靠岸的"快"是感知速度：原文立即可见（PDF 直接渲染）、只译视口、译文渐进流入——模型并不更快。

### 2.3 细节问题
- `openai_compat.py:75`：每次翻译新建 `httpx.AsyncClient()`，47 次请求 = 47 次 TCP+TLS 握手。
- 两层批失败回退（provider:120 / processor:212）均为 `for + await` 串行，且占住并发额度。
- `_jobs` 字典无限增长（processor.py:40），内存泄漏。

## 3. 质量瓶颈

- **逐段盲译**：`_system_prompt`（openai_compat.py:25）零上下文，每 10 段一批批批盲译 → 同一术语在不同批次译法漂移、代词指代丢失。专业工具标配是两遍法（先抽术语表再带语境翻译）。
- `max_tokens=8192` 装 10 个学术段落，截断风险：`translate()` 不查 `finish_reason`（OCR 查了，翻译没查）→ 段数不匹配 → 静默回退串行，又慢又无感知。
- 翻译缓存键 `(text_hash, lang, model)` 不含提示词版本（OCR 侧有 `TEXT_LAYER_MODEL=v2` 版本控制，翻译侧没有，不一致）——改提示词后旧缓存照样命中。
- 模型短板已解决（deepseek-ai/DeepSeek-V4-Flash 实测 1.17s、质量佳）。

## 4. 排版瓶颈

- **数据模型里 `position` 全为 0**（processor.py:37）：对齐从来不存在。双栏对照靠 block 顺序 + `minHeight = original.length × 0.8`（BilingualPage:58）拍脑袋估算；中文比英文短，系数必然错，错位累积。滚动同步按百分比，两栏高度不同即漂移。
- 知云/靠岸走 **PDF 原生渲染 + 坐标级对照**；本项目走 **Markdown 重建**（pymupdf4llm），天然丢失多栏阅读顺序、矢量图、公式位置。此路线能到 80 分，到不了 100 分——**这是选型时注定的天花板，不是 bug**。
- 叠加细节伤：跨页段落被 `_split_page` 按页切成两块；无公式渲染（MarkdownText 无 remark-math/KaTeX）。

## 5. 修复优先级（已纳入重构路线图）

| 优先级 | 改动 | 性质 | 收益 |
|--------|------|------|------|
| P0（阶段1） | 前端渐进渲染 + 去遮罩 | 前端少量改动 | 感知速度质变：原文秒开、译文边译边出 |
| P0（阶段1） | AsyncClient 模块级复用 | 细节 | 每请求省 200–400ms |
| P1（阶段2） | finish_reason 检查 + 缓存版本号 + 跨页合并 | 细节 | 消除静默降级与缓存陷阱 |
| P2（阶段2/3） | 术语表两遍法；KaTeX | 架构补丁 | 质量与公式可读性上台阶 |
| P3（阶段4） | 原生渲染路线评估（决策门 D6） | 重新选型 | 保真度质变，工程量大，需用户确认 |

**一句话**：不缺模型也不缺并发，缺"渐进呈现"；质量差源于"无文档视角"；排版乱是重建路线的固有代价。先做阶段 1 再测，体感大概率立刻改观。
