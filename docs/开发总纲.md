## 1. 产品愿景与范围（锁定）

### 1.1 目标
- **个人本地使用**：配置一次 API Key，开箱即可双语阅读。
- **开源复刻**：他人 clone 后按文档可跑起来（平台范围见第 9 章 Q2）。

### 1.2 核心功能（MVP 必含）
| 功能 | 描述 |
|------|------|
| PDF 上传 | 选择/拖拽 PDF |
| OCR 识别 | SiliconFlow PaddleOCR-VL-1.5 提取文本+版面 |
| 段落级翻译 | 调用 LLM 按 block 翻译 |
| 左右对照 | 双栏同步滚动（原文/译文） |
| 紧跟模式 | 原文段下嵌入译文 |
| 配置页 | 填写 API Key，可切换 provider |
| 本地缓存 | 已翻译结果落盘，避免重复调用 |

### 1.3 明确不做（非目标）
- 不做 Word/Excel/PPT 等其它格式（仅 PDF）。
- 不本地部署 OCR/翻译模型（全部走云端 API，exe 不含模型权重）。
- 不做在线账号 / 多用户 / 协作。
- 不做移动端。

## 3. 架构与数据流（基于真实代码）

### 3.1 分层
```
React 前端 (src/)
   │  invoke (Tauri 命令)
   ▼
Rust 后端 (src-tauri/src/commands.rs)  —— 进程内，reqwest 调本地 8000
   │  HTTP POST/GET
   ▼
FastAPI 后端 (backend/)  —— 127.0.0.1:8000
   │  HTTPS + Bearer Key
   ▼
SiliconFlow API（OCR /generate、翻译 /chat/completions）
```

**分发方式（已确认 D1）**：FastAPI 以 **Tauri sidecar** 形式随 exe 打包（内嵌 Python 解释器 + venv），应用启动由 Rust 拉起本地 8000 端口；分发包仅 Windows（D2）。

### 3.2 当前真实数据流（含断点）
1. 用户在 `MainPage` 选 PDF（dialog）→ **立即**调用 `run_pipeline`（注：当前无“开始识别”按钮，选完即处理，与旧文档不符）。
2. Rust `run_pipeline` → `POST /api/pipeline/run`。
3. FastAPI `run_pipeline` 立即返回 `{job_id, status:"running"}`，并 `asyncio.create_task` 后台处理（**fire-and-forget，未持有任务句柄**）。
4. 后台：`call_ocr`（PDF 转 base64 → SiliconFlow `/generate`）→ 逐 block 调 `translate_text`。
5. 结果仅存内存 `_jobs[job_id]`。
6. **断点①（致命）**：前端 `useOcr` 只读取首次返回的 `running`，**从不轮询 `/api/pipeline/status/{job_id}`** → 结果页面永远不刷新 → 应用当前“不可用”的根因。
7. **断点②**：`BilingualPage` / `InlinePage` 只渲染 `pages[0]`，无多页导航、`PdfViewer` 是空桩。

### 3.3 目标链路
前端轮询 status（或 SSE/WebSocket）直到 `done`/`failed` → 拿到 `pages` → 渲染（含多页导航）。

## 4. 数据模型与接口契约（锁定）

### 4.1 配置文件（磁盘）
路径：`~/.pdf-reader/config.json`（Windows：`%APPDATA%/pdf-reader/config.json`）。
**字段全部 snake_case**（旧文档 5.1 误写 camelCase `apiKey`/`apiUrl`，以本文件为准）：
```json
{
  "ocr": {
    "provider": "siliconflow",
    "api_key": "",
    "api_url": "https://api.siliconflow.cn/v1",
    "model": "PaddlePaddle/PaddleOCR-VL-1.5",
    "optional_payload": { "useDocOrientationClassify": false, "useDocUnwarping": false, "useChartRecognition": false }
  },
  "translate": {
    "provider": "siliconflow",
    "api_key": "",
    "api_url": "https://api.siliconflow.cn/v1",
    "model": "Qwen/Qwen2.5-7B-Instruct",
    "target_language": "en",
    "source_language": "zh"
  },
  "ui": { "default_mode": "bilingual", "theme": "light" }
}
```

### 4.2 核心数据结构（前后端一致）
- `TextBlock { block_id:int, page:int, original:str, translated:str, position:{y_start:int,y_end:int} }`
- `PageResult { page:int, blocks:TextBlock[] }`
- `PipelineResult { job_id:str, status:"running"|"done"|"failed", progress:int, pages:PageResult[] }`
（TS 定义见 `src/types/index.ts`，Rust 定义见 `src-tauri/src/commands.rs` 的 `AppConfig` 等。）

### 4.3 翻译 Provider 接口契约（可扩展抽象，已确认 D3）
采用**注册表 + 统一接口**模式，便于复刻者自行接入新厂商：
- 统一接口（所有 provider 必须实现）：
  - `translate(text, source_lang, target_lang, config) -> str`
  - `translate_batch(texts, source_lang, target_lang, config) -> list[str]`
- 注册表：`PROVIDERS = { "siliconflow": ..., "openai": ..., ... }`，由 `provider` 字段分发。
- **默认实现**：`siliconflow`（OpenAI 兼容 chat/completions）。
- **OpenAI 兼容族**：OpenAI 及一切 OpenAI 兼容端点（DeepSeek、Qwen、各家兼容服务）共用一个 `openai_compatible` 实现，仅 `api_url`/`api_key`/`model` 不同 → 一次实现覆盖多数厂商。
- **独立适配器**：Google Translate、DeepL 协议不同，作为独立 provider 后续实现；未实现前 UI 列表保留但标注“即将支持”，禁止静默调用失败。
- 现状：后端仅 `siliconflow` 实现（`translate/base.py` 函数式）；`openai`/`google`/`deepl` 后端未实现（见 6.R8）。

### 4.4 FastAPI 接口（现状真实）
| 方法 | 路径 | 用途 |
|------|------|------|
| GET | `/api/health` | 健康检查：Tauri 侧据此判断内嵌 sidecar 已就绪 |
| POST | `/api/pipeline/run` | `{file_path} → {job_id, status:"running"}`（**异步**，须轮询 status） |
| GET | `/api/pipeline/running` | `→ [{job_id, file_path, progress}]`（阶段11-T5：F5 后前端自动重接管用） |
| GET | `/api/pipeline/status/{job_id}` | `{job_id, status, progress, pages, error}` |
| POST | `/api/ocr/process` | `{file_path} → pages` |
| POST | `/api/translate/batch` | `{texts, source_lang, target_lang} → [str]` |
| POST | `/api/config/reload` | 显式热重载配置（R7） |
| GET | `/api/config` | 读取当前配置（dev 桥接：浏览器模式前端加载配置用） |
| POST | `/api/config` | 写入配置（dev 桥接：浏览器模式前端保存配置用） |
| POST | `/api/upload` | 上传 PDF，返回服务端路径（dev 桥接：浏览器无真实路径时） |
| GET | `/api/file/raw?path=` | 返回文件原始字节（dev 桥接：缩略图经 URL 读取） |
| GET | `/api/file/exists?path=` | 文件是否存在（dev 桥接：对应 check_file_exists） |
| GET | `/api/asset?path=` | 按路径返回 cache/ 内图片（仅限 cache_dir 之内，防任意读） |
| POST | `/api/figure/translate` | 表格快照按需译制图（仅 tab_*，结果落盘缓存幂等） |
| POST | `/api/block/translate` | 单块手动翻译/重翻（与全文管线同缓存 key） |
| POST | `/api/block/formula` | 块级公式识别 → LaTeX（(pdf_hash,page,bbox,model) 缓存） |
| GET | `/api/docs` | 文档索引列表（主页"已翻译文章"，含 file_exists 标记） |
| POST | `/api/docs/open` | 按 doc_id 从缓存重建会话（秒开，零翻译调用） |
| POST | `/api/docs/move` | 文档移动到文件夹（folder_id=null 归未分类） |
| POST | `/api/docs/rename` | 改文献显示名（`{doc_id, title}`，仅索引标题不动源文件） |
| POST | `/api/folders`（/rename /delete） | 文件夹管理（2026-09-09 靠岸学术改版） |
| POST | `/api/log` | 前端错误上报落盘（logs/frontend.log，打包版排查主线索） |
| POST | `/api/export/babeldoc` | BabelDOC 双语 PDF 导出启动（阶段9；缓存命中/任务幂等） |
| GET | `/api/export/babeldoc/cached?file_path=` | 探测该文档是否已有排版对照产物（前端免确认直接打开缓存） |
| GET | `/api/export/babeldoc/running` | 列出运行中的排版对照导出任务（App 启动静默重接管） |
| GET | `/api/export/babeldoc/{job_id}` | 导出进度查询（内存任务表） |
| DELETE | `/api/export/babeldoc/{job_id}` | 取消导出（kill 子进程） |
- 监听 `127.0.0.1:8000`，CORS `*`，无 Pydantic 校验（直接用 dict）。
- 带 `dev` 标注的端点仅用于**本地开发/人工测试**（纯浏览器模式）。生产环境由 Tauri IPC + `convertFileSrc` 替代，不会暴露这些 HTTP 端点给外部。

### 4.5 Tauri 命令（现状真实）
`load_config` / `save_config` / `run_pipeline` / `get_pipeline_status` / `check_file_exists` / `get_cache_dir`

### 4.6 前端「双模桥接」（`src/lib/bridge.ts`）
前端不直接调用 Tauri 也不直接 `fetch` 后端，而是统一经 `src/lib/bridge.ts`：
- 运行在 **Tauri 内**（`__TAURI_INTERNALS__` 存在）→ 走原生 `invoke` / `open` / `convertFileSrc`。
- 运行在 **纯浏览器**（`npm run dev`，本机无法编译 Rust 时）→ 自动改走 `fetch` 到 `http://localhost:8000`，并用 `/api/upload` 把选中的 PDF 上传到后端换取服务端路径，用 `/api/file/raw` 提供缩略图 URL。
- 桥接层对调用方**保持与 Tauri 命令一致的返回形态**（如 `run_pipeline` 仍返回 JSON 字符串），上层 `useOcr` / `configStore` 无需感知环境。
- **约束例外说明**：主文档 §2.1-2 / §7-2 规定"前端禁止直连第三方 API"，dev 桥接仅在**非 Tauri 环境**连**本地后端**（非外部 API），不触碰任何第三方服务、不硬编码 Key，因此不违反该约束。

## 10. 构建与验证（重要）

### 10.1 内嵌后端（sidecar）构建流程
打包自包含 exe 前，**必须先**构建后端 sidecar：

```powershell
# 1) 构建内嵌后端 → src-tauri/sidecar/pdf-backend-<triple>.exe
powershell -ExecutionPolicy Bypass -File scripts/build-backend.ps1

# 2) 再打包桌面应用（sidecar 会一并打入）
npm run tauri build
```

`scripts/build-backend.ps1` 会自动探测 `.venv`/`python`、按需安装 PyInstaller、
从 `rustc -vV` 推断目标三元组，并对 uvicorn 做 `--collect-all` 收集。

### 10.2 开发态运行
开发态**不会**拉起内嵌 sidecar（避免与手动启动的后端争用 8000 端口）：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/dev-start.ps1
```

### 10.3 环境要求与已知限制 ⚠️
- **Windows 10/11 SDK 必需**：Rust 的 MSVC 目标链接需要 Windows 10/11 SDK。当前开发机**仅安装了 Windows Kits 8.1**，缺少 10/11 SDK，因此 `cargo check` / `tauri build` **无法在该机完成**（失败在链接阶段，非代码问题）。

## 11. OCR 端点验证发现（R6，待选型）⚠️

> 2026-09-04 技术验证结果：**原 OCR 实现调不通，属 P0 级阻断。**

### 11.1 现有实现的错误
`backend/ocr/siliconflow.py` 当前：
```python
payload = {"model": model, "file": file_data, "fileType": 0, "optionalPayload": ...}
resp = client.post(f"{api_url}/generate", ...)
data["result"][...]["layoutParsingResults"]
```
这是 **PaddleOCR 自托管 `layout-parsing` 服务**的请求/响应格式（需本地起服务，端口 8080），**SiliconFlow 云 API 根本没有 `/generate` 端点**。

### 11.2 SiliconFlow 平台的真实调用方式（已查证官方文档）
PaddleOCR-VL-1.5 在 SiliconFlow 上通过标准 OpenAI 兼容接口提供：
```
POST https://api.siliconflow.cn/v1/chat/completions
{
  "model": "PaddlePaddle/PaddleOCR-VL-1.5",
  "messages": [{"role":"user","content":[
     {"type":"image_url","image_url":{"url":"data:image/jpeg;base64,....","detail":"high"}},
     {"type":"text","text":"OCR:"}
  ]}],
  "max_tokens": 8192, "temperature": 0.01
}
→ choices[0].message.content  # markdown 文本
```
**关键约束**：该接口只接受**图片**（image_url），**不接受 PDF 文件**。因此无论怎么改，都必须先把 PDF 每页渲染成图片再送入模型。

### 11.3 由此带来的架构影响
1. 需要在流水线中引入 **PDF→图片** 步骤（建议 `PyMuPDF`/`fitz`，单 pip 包跨平台，无外部依赖）；或用 `pdf2image`（依赖 poppler，不推荐）。
2. OCR 返回的是**整页 markdown 文本流**，不再有 `layoutParsingResults` 的 bbox/分块结构 → 现有 `PageResult.blocks` 数据模型需调整（整页一块 vs 细分块），对照阅读的对齐方式也受影响。
3. 失去精确 bbox 后，若要“译文贴回原位置”需另寻方案（超出当前范围）。

### 11.4 待用户选型的三个方向（见尾声选择题）
- **A（纯 API，推荐起步）**：PyMuPDF 逐页转图 → 逐页调 `/chat/completions` → 整页 markdown 作为一“块”。无需本地模型，最易复刻；代价是无细分块结构、长文档 token 成本高。
- **B（本地 layout 服务）**：保留 `layoutParsingResults` 的多块结构，但需在本地部署 PaddleOCR layout 服务（需 GPU/较大依赖），违背“轻松复刻”。
- **C（混合）**：PyMuPDF 优先提取**文本层**（有文本层的 PDF 零成本、零网络）；无文本层（扫描件）才走 OCR。兼顾速度与成本。
